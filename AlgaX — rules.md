# AlgaX — Engineering & Product Rules

This document contains the general rules that every developer or coding agent must follow while working on AlgaX.

These rules apply to every phase of development.

`plan.md` remains the source of truth for product, scientific, business, and domain decisions.

`architecture.md` remains the source of truth for technical architecture, data structures, APIs, infrastructure, and system design.

`prompt.md` defines the implementation-agent workflow and non-negotiable project constraints.

This file defines the quality, coding, UI, communication, and engineering standards.

---

# 1. General Principle

Build AlgaX as a real software product, not as a collection of AI-generated demonstrations.

Every implementation should have a clear purpose within the product.

Prefer:

- simple solutions
- maintainable code
- explicit behavior
- predictable architecture
- meaningful naming
- real validation
- explainable logic

Avoid:

- unnecessary complexity
- artificial abstractions
- placeholder implementations disguised as complete features
- fake functionality
- excessive dependencies
- duplicated logic
- unnecessary configuration

Do not build something merely because it looks impressive.

Build what the product actually needs.

---

# 2. Read the Project Documentation First

Before implementing a feature, understand the relevant requirements from:

1. `plan.md`
2. `architecture.md`
3. `prompt.md`
4. this `rules.md`

Do not assume previous conversation context exists.

Do not invent requirements that contradict the project documents.

If the documents already define a solution, follow that solution.

If something is genuinely undefined, make the smallest reasonable decision and document the assumption.

---

# 3. Human-Like Code

Code should look like it was written and maintained by an experienced human developer.

Use:

- meaningful variable names
- descriptive function names
- clear module boundaries
- straightforward control flow
- appropriate comments
- consistent formatting
- logical file organization

Avoid code that looks automatically generated.

Do not create:

- excessively long functions
- deeply nested conditionals
- meaningless helper functions
- unnecessary interfaces
- excessive generic abstractions
- repetitive comments
- comments that merely restate the code
- huge configuration objects without justification

Prefer readable code over clever code.

Example:

Good:

```python
growth_rate = calculate_growth_rate(environment, species_profile)
```

Avoid:

```python
result = process_data(x, y, z)
```

when the actual meaning can be expressed clearly.

---

# 4. Comments

Comments should explain WHY something exists, not repeat WHAT the code does.

Good:

```python
# Keep the previous model version so historical estimates remain reproducible.
```

Avoid:

```python
# Increment the model version.
model_version += 1
```

Do not fill the codebase with unnecessary comments.

Use comments when they provide meaningful context, scientific reasoning, architectural reasoning, or important constraints.

---

# 5. Scientific Code

Scientific calculations must be explicit and traceable.

Do not hide scientific formulas inside unexplained code.

For important calculations:

- use meaningful variable names
- preserve units
- document assumptions
- separate model logic from infrastructure
- make calculations testable
- keep model versions explicit

For example, the growth model should clearly represent:

```text
Light limitation
Temperature limitation
pH limitation
Nitrogen limitation
        ↓
Growth rate
        ↓
Biomass change
```

Do not replace the project's mechanistic model with arbitrary formulas simply because another approach is easier to implement.

Do not invent scientific parameters without justification.

---

# 6. Units Are Mandatory

Never silently mix units.

Whenever possible, make units obvious through:

- variable names
- model documentation
- schema definitions
- comments where necessary
- API documentation
- UI labels

Examples:

```text
temperature_c
biomass_g_per_l
nitrogen_mg_per_l
energy_kwh
co2_kg
```

Avoid ambiguous names such as:

```text
temperature
amount
value
rate
```

when the unit materially affects interpretation.

---

# 7. No Fake Data in Production Logic

The simulator may generate synthetic data because the hackathon does not use physical sensors.

However, synthetic data must be generated by the project's defined dynamical simulation.

Do not use independent random values to simulate biological behavior.

Do not do:

```python
temperature = random.uniform(...)
ph = random.uniform(...)
biomass = random.uniform(...)
nitrogen = random.uniform(...)
```

and present that as realistic telemetry.

Instead:

```text
Environment
    ↓
Biological state
    ↓
Derived measurements
    ↓
Sensor noise
    ↓
Sensor reading
```

Randomness may be used for realistic measurement noise, outliers, or failures where the architecture allows it.

It must not replace the underlying environmental and biological model.

---

# 8. Separate Simulation, Model, and Presentation

Maintain clear separation between:

```text
Simulation
Model Engine
Persistence
API
Frontend
```

The frontend must not contain scientific business logic that belongs in the backend/model layer.

The database must not contain hidden business logic.

The simulator must communicate through the defined ingestion contract.

The growth engine must not depend on React or frontend code.

---

# 9. Determinism and Reproducibility

Where the scientific model is expected to be deterministic, the same:

- model version
- parameters
- inputs
- initial state
- timestep

should produce reproducible results.

If randomness is intentionally introduced, use a controlled seed where appropriate.

Do not make scientific results randomly change between identical model runs without a documented reason.

---

# 10. Provenance

Derived data must remain traceable.

Maintain the project's intended chain:

```text
SensorReading
    ↓
EnvironmentalSnapshot
    ↓
ModelRun
    ↓
BiomassEstimate
    ↓
CarbonEstimate
    ↓
Anomaly
    ↓
VerificationReport
```

Do not create shortcuts that destroy traceability.

Every derived result must retain the provenance required by `plan.md` and `architecture.md`.

---

# 11. Error Handling

Handle errors deliberately.

Do not silently swallow exceptions.

Avoid:

```python
try:
    ...
except:
    pass
```

Errors should provide enough information to diagnose the problem without exposing secrets.

Use appropriate:

- HTTP status codes
- validation errors
- application errors
- logging
- user-facing messages

Do not expose stack traces or secrets to normal users.

---

# 12. Logging

Logs should help developers understand what happened.

Use logs for:

- application startup
- important model executions
- ingestion failures
- scheduled jobs
- scenario injection
- report generation
- verification operations
- unexpected failures

Do not log:

- passwords
- API keys
- authentication tokens
- unnecessary personal information
- sensitive credentials

Do not fill logs with useless messages on every trivial operation.

---

# 13. Database Rules

Database design must follow `architecture.md`.

Do not:

- casually rename fields
- repurpose fields
- remove provenance
- bypass migrations
- manually modify production schema
- store structured data as arbitrary strings when the schema already provides a proper structure

Use migrations for schema changes.

Preserve historical records when the product requires auditability.

---

# 14. API Rules

APIs should be:

- predictable
- clearly named
- validated
- versionable where required
- documented
- consistent

Request and response structures should use meaningful names.

Do not return unnecessary fields.

Do not expose internal implementation details unless the API contract requires them.

Validate incoming data at the API boundary.

---

# 15. Frontend Rules

The frontend should feel like a professional environmental intelligence platform.

It should not look like a generic AI dashboard template.

Use:

- clear hierarchy
- restrained visual design
- meaningful spacing
- readable typography
- consistent cards
- purposeful charts
- useful status indicators
- clear empty states
- useful loading states
- useful error states

Avoid:

- excessive gradients
- excessive glassmorphism
- excessive glowing effects
- huge decorative elements
- unnecessary animations
- excessive rounded cards
- random dashboard widgets
- meaningless statistics

The interface should prioritize information clarity.

---

# 16. No Unnecessary Emojis

Do not use emojis as decoration throughout the application.

Avoid interfaces such as:

```text
🌱 Biomass
🌡️ Temperature
💧 Water
🚨 Alerts
📊 Analytics
```

Use proper icons from the project's chosen icon library where appropriate.

Icons should communicate meaning, not decorate every heading.

Do not add emojis to:

- navigation
- dashboard headings
- buttons
- cards
- notifications
- reports

unless there is a specific product reason to do so.

The product should feel professional and scientific.

---

# 17. UI Text Should Sound Human

Do not use generic AI-generated phrases such as:

- "Unlock powerful insights"
- "Revolutionize your carbon journey"
- "Harness the power of AI"
- "Take your sustainability to the next level"
- "Smart insights for a smarter future"

unless marketing copy specifically requires them and they genuinely fit the product.

Prefer direct language:

```text
Carbon Removal
Net carbon removed after operational emissions.

Pond Health
Current environmental and biological condition.

Growth Limitation
Nitrogen is currently the dominant growth limitation.

Verification Status
Evidence package ready for verifier review.
```

The product should speak like a professional scientific system.

---

# 18. Dashboard Design

Every metric shown on the dashboard should answer a useful question.

Bad:

```text
12
Smart Insights

87
Performance Score

94
AI Index
```

Good:

```text
Net Carbon Removed
1,284 kg CO₂

Biomass
312 kg

Average Growth Rate
4.8% / day

Active Anomalies
2
```

If a metric has no meaningful product purpose, do not display it.

---

# 19. Charts

Charts must communicate actual information.

Every chart should have:

- meaningful title
- readable axes
- units
- appropriate time range
- useful tooltip
- understandable legend when necessary

Do not create charts simply to make the dashboard look busy.

Avoid showing five charts that communicate the same information.

---

# 20. Loading, Empty, and Error States

Every important screen should handle:

### Loading

Show a meaningful loading state.

### Empty

Explain why there is no data.

Example:

```text
No telemetry available yet.

The pond simulator has not published its first reading.
```

### Error

Explain what went wrong in human language.

Example:

```text
Unable to load pond telemetry.

The monitoring service may be temporarily unavailable.
```

Do not leave blank white sections.

---

# 21. Responsive Design

The website must work on:

- desktop
- laptop
- tablet
- smaller screens where practical

Do not treat mobile responsiveness as an afterthought.

However, do not compromise the desktop monitoring experience merely to force every dashboard component into a mobile layout.

---

# 22. Accessibility

Use:

- semantic HTML
- keyboard-accessible controls
- readable contrast
- labels for inputs
- accessible chart explanations where practical
- meaningful button text

Do not rely only on color to communicate status.

For example, don't use only:

```text
red = critical
green = healthy
```

Also provide:

```text
Critical
Healthy
```

---

# 23. Animations

Animations should communicate state or improve understanding.

Use animation for:

- live telemetry updates
- transitions
- loading
- meaningful state changes

Do not animate every component.

Avoid:

- constant floating elements
- excessive hover effects
- distracting particle backgrounds
- unnecessary page transitions

The application is an operational/scientific platform, not a gaming website.

---

# 24. Dependencies

Before adding a dependency, ask:

1. Is it actually needed?
2. Does the architecture already provide an alternative?
3. Does it materially improve the product?
4. Is it maintained and appropriate?

Do not install libraries for trivial functionality.

Keep the dependency footprint reasonable.

---

# 25. Security

Never commit:

- API keys
- passwords
- private tokens
- production credentials
- private certificates

Use environment variables and secure configuration.

Validate user input.

Apply authentication and authorization according to the phase requirements.

Never trust frontend authorization alone.

---

# 26. No Premature Features

Do not implement future phases early merely because they are interesting.

For example:

If the current phase is Growth & Biomass Engine, do not suddenly implement:

- investor dashboards
- billing
- mobile apps
- carbon registry integrations
- advanced AI
- unrelated analytics

Complete the current phase correctly.

---

# 27. No Superficial Features

Prefer five deeply implemented features over twenty shallow ones.

A feature is not complete because:

- a button exists
- a page exists
- a card displays a hardcoded number
- an API returns mock JSON
- a modal opens

A feature is complete when the underlying behavior works and is validated.

---

# 28. No Hardcoded Production Results

Never hardcode results merely to make the UI look complete.

Avoid:

```javascript
const biomass = 284.7;
const carbonRemoved = 1284;
```

if those values are supposed to come from the actual system.

Mock data is acceptable only for explicitly defined foundation/prototype boundaries and must not accidentally become production logic.

---

# 29. Scientific Honesty

AlgaX must clearly distinguish:

```text
Simulated Observation
Model Estimate
Derived Calculation
Evidence
Verification Status
```

Never represent simulated hackathon data as real physical sensor measurements.

Never claim that the platform itself certifies carbon removal or issues carbon credits unless the product requirements are explicitly changed and the necessary external authority exists.

Do not exaggerate scientific certainty.

When appropriate, expose:

- confidence
- provenance
- model version
- assumptions
- data source

---

# 30. Testing

Tests should verify behavior, not merely code coverage.

Prioritize:

- scientific calculations
- edge cases
- API validation
- database relationships
- provenance
- deterministic behavior
- scenario behavior
- carbon accounting constraints
- anomaly detection
- report generation

For scientific functions, test known input/output relationships.

For example:

```text
Ideal conditions
→ higher growth

Strong nitrogen limitation
→ lower growth

Zero nitrogen
→ nitrogen limitation reaches its defined boundary

Extreme temperature
→ reduced growth
```

Do not create tests that simply mirror implementation without validating behavior.

---

# 31. Before Declaring a Feature Complete

Ask:

- Does it actually work?
- Is it connected to the correct data source?
- Is it using the project's intended architecture?
- Is it tested?
- Does it handle errors?
- Does it preserve provenance?
- Does it use correct units?
- Does it behave correctly at edge cases?
- Does it introduce unnecessary complexity?
- Does the UI communicate the result clearly?
- Does it contradict anything in `plan.md`?
- Does it contradict anything in `architecture.md`?

If the answer to an important question is no, the feature is not complete.

---

# 32. Git Commits

Commits should describe actual completed work.

Prefer:

```text
feat: implement pond telemetry ingestion
```

```text
feat: add biomass growth model
```

```text
fix: preserve model run provenance for biomass estimates
```

```text
test: add nitrogen limitation scenarios
```

Avoid:

```text
update
```

```text
changes
```

```text
final
```

```text
done
```

---

# 33. Documentation

Document important architectural and scientific decisions.

Do not write documentation for every obvious line of code.

Documentation should help a future developer understand:

- why something exists
- how the system works
- scientific assumptions
- important limitations
- configuration
- API contracts
- setup
- testing
- deployment

---

# 34. AI Coding Agent Behavior

When working as an AI coding agent:

- inspect before modifying
- understand existing code
- avoid unnecessary rewrites
- reuse working components
- do not delete working functionality without reason
- test changes
- fix failures before moving forward
- report what actually happened

Never claim:

> "Implemented successfully"

unless the implementation was actually tested.

Never claim a test passed if it was not executed.

Never hide an unresolved error.

---

# 35. When Requirements Are Ambiguous

Do not ask unnecessary questions if the project documents already provide the answer.

When something is genuinely undefined:

1. identify the ambiguity
2. choose the smallest reasonable solution
3. keep it consistent with the architecture
4. document the assumption
5. continue implementation

Do not silently make large architectural decisions.

---

# 36. Final Quality Standard

AlgaX should feel like a serious technical product built by a small professional engineering team.

The desired characteristics are:

- scientifically grounded
- technically coherent
- explainable
- reproducible
- maintainable
- visually professional
- restrained
- human-readable
- honest about limitations

The goal is not to make the project look AI-generated.

The goal is to make the project look like a real product that happens to use sophisticated modeling and automation.

---

# 37. Priority Order

When making implementation decisions, prioritize:

1. Correctness
2. Scientific integrity
3. Product requirements
4. Architecture consistency
5. Data provenance
6. Testability
7. Maintainability
8. User experience
9. Visual polish
10. Convenience

Never sacrifice correctness merely to make a feature look impressive.

---

# 38. Final Rule

When in doubt:

**Build less, but build it correctly.**

Do not add complexity, decoration, data, AI, or features unless they have a clear purpose in AlgaX.

Every part of the system should contribute to the core chain:

```text
Observe
→ Model
→ Measure
→ Explain
→ Account
→ Report
→ Support Verification
```
